# Selective-VPN-Bypass — Independent Product & Failure-Mode Audit
**2026-11-22 KST · status: engineering review, not a security certification**

This review reconstructs the complete behavior of the Windows portable application from `main.go`, `embedded_worker.go`, `src/Core.ps1`, `src/Gui.ps1`, `src/Worker.ps1`, `tests/*`, the two Actions workflows, README and earlier project requirements. It separates **verified code behavior**, **failure hypotheses**, and **unverified environment assumptions**. No user device, production school network or live VPN was accessed.

## 1. Originally intended contract versus current implementation

| Requirement / user context | Implementation | Limitation / burden |
| --- | --- | --- |
| Default VPN connection remains managed by SoftEther; exception list is explicit | GUI `Apply` creates NRPT and selected IPv4 /32 routes | This is an IP-route approximation, not complete site- or browser-level routing. The application should not be used to evade access rules on networks the user does not administer. |
| Lightweight portable GUI/EXE, no repeated manual script changes | Go EXE embeds PowerShell and creates runtime scripts in LocalAppData | EXE folder holds JSON state while runtime scripts/logs live elsewhere; moving ZIP or switching folders breaks continuity. |
| Persist add/remove/list and support explicit IPv4 | `Core.ps1` JSON and WinForms list | Add is saved immediately but not active until next Apply; saved/applied distinction was previously unclear. |
| SoftEther/Tailscale routes retained; safe Restore | IPv4 default unchanged intentionally; state-driven cleanup | A changed interface, route, new DNS response or conflicting installation can leave partial state; the app lacks a guided recovery screen. |
| Enter-to-add, Delete-to-remove, minimal mouse usage | KeyDown handlers present in Gui.ps1 | Physical keyboard, accessibility, DPI and screen-reader testing not in CI. |
| GitHub Actions portable artifact; user downloads directly | `SelectiveVPNBypass-Portable-Windows-x64`, no Actions bot commits | CI success ≠ all real-user network states supported. |

## 2. Runtime state inventory

```text
Portable EXE directory
  ├─ SelectiveVPNBypass_GUI.exe             (trusted binary? not signed)
  ├─ Selective-VPN-Bypass.domains.json      (desired saved exceptions)
  └─ Selective-VPN-Bypass_v3.state.json     (v6 schema: state journal)

%LOCALAPPDATA%/SelectiveVPNBypass/runtime-v4/
  ├─ Gui.ps1 / Core.ps1 / Worker.ps1        (per-launch extraction)
  └─ startup.log                           (overwritten on launcher start)

%TEMP%/svb-<guid>.log                        (per-operation, deleted after read)
Windows configuration
  ├─ NRPT namespace rules
  ├─ ActiveStore IPv4 routes
  └─ interface/gateway/DNS state            (may change independently)
```

No single component proves consistency across these locations. Applied-state verification must independently inspect Windows objects; state-file presence alone is not proof of successful application.

## 3. Audit findings — evidence and priority

**Priority definitions:** P0 blocks claims of general safe recovery; P1 is a likely functional/user burden defect; P2 is quality/maintainability. `Verified` means the cited source establishes behavior, not necessarily that the failure was reproduced on a live Windows machine.

| ID | Priority | Finding & source | Evidence type | Consequence |
| --- | --- | --- | --- | --- |
| R-01 | **P0** | `Core.ps1` Restore consults saved rule IDs and pending namespaces; a missing, corrupted or moved state file is not automatically reconciled with the OS. `Restore-Own` returns early on no state. | Verified source; live orphan scenario not exhaustively tested | Unremoved NRPT rules may remain without an accessible recovery UI. |
| R-02 | **P0** | `Core.ps1` uses a config-directory-derived `Local\\` mutex. Different portable directories, sessions and other programs are not globally serialized. NRPT ownership is a non-secret Comment string. | Verified design boundary | Multiple copies may adopt or remove each other's same-tag rules. |
| R-03 | **P0** | The elevated embedded worker executes the EXE's embedded source, but the portable executable is unsigned and its containing directory may be user writable. External state JSON is read at privilege level. | Verified source; exploitability not tested | Executable and configuration trust boundaries need an installation/security model. |
| R-04 | **P1** | GUI `Update-Status` previously displayed `Applied: <Test-Path(state)>`. This is journal existence, not verified OS state. | Verified source; **GUI label patch committed** | False confidence after partial Apply/crash/Restore. |
| R-05 | **P1** | GUI Add previously cleared input as soon as the worker started; on permission/filesystem failure text was lost. | Verified source; **deferred-clear patch committed** | Repeated user effort after failure. |
| R-06 | **P1** | `Gui.ps1` 150 ms timer has no worker deadline, cancellation or escalation path while buttons are disabled. | Verified source | Hung DNS or OS call leaves the UI actionable only by closing/restarting. |
| R-07 | **P1** | `Core.ps1` aliases `Wi-Fi` and `VPN - VPN Client` are hard-coded, as are specific Windows command expectations. | Verified source | Localized adapters, Ethernet, renamed VPN NIC, or absence of a default route cause failure. |
| R-08 | **P1** | Apply uses the first Wi-Fi DNS server's A answers as a snapshot; IPv6, DoH, CDN sharing and DNS TTL changes are not fully accounted for. | Verified source + documented limitation | Routing outcomes can drift; a saved exception is not a domain isolation guarantee. |
| R-09 | **P1** | `Save-Json` creates a backup for atomic replace but deletes it in `finally`, even on exception; there is no durable state recovery snapshot. | Verified source | Filesystem errors may still require manual recovery; backup retention is insufficient. |
| R-10 | **P1** | `main.go` rewrites a common `runtime-v4` script set and `startup.log`; extraction uses a fixed `.new` path without inter-process startup lock. | Verified source; race not reproduced | Overlapping launches can interfere with startup or logs. |
| R-11 | **P1** | `Restore-Own` refuses interface index changes; it does not offer a guided 'detect only' report and instruction path for stale journals. | Verified source | Network roaming/reboots can leave a user-facing Restore failure with no clear resolution. |
| R-12 | **P2** | GUI uses process exit code and a transient log rather than a typed result with actual route/NRPT reconciliation status. | Verified source | 'Completed' can mean command completion, not complete network verification. |
| R-13 | **P2** | No recovery-specific UX for file missing, UAC cancellation, operation timeout, state corruption or competing portable folders. | UX gap found in source | Requires users to diagnose PowerShell errors and edit/move files manually. |
| R-14 | **P2** | GUI and Core duplicate input validation; PowerShell orchestration/UI callbacks share a large script. | Verified source | Drift and regression risk, difficult unit testing. |
| R-15 | **P2** | Main Actions test GUI button reflection; it does not exercise real keyboard/DPI/UAC/SoftEther paths. The isolated live test exits a child normally with incomplete journal, rather than injecting forced process termination at every operation. | Verified test source | Successful CI is narrower than 'crash safe under all failures'. |
| R-16 | **P2** | `actions/checkout@v4`, `setup-go@v5`, `upload-artifact@v4` are major-tagged, not exact SHA pinned. | Verified workflow | Reproducibility and supply-chain assurance can improve. |
| R-17 | **P2** | Fresh portable folders do not import previous JSON state by design; documentation and GUI do not present a safe migration/export path. | Verified code + prior user request | New ZIP extraction may appear to have 'lost' exceptions; careless migration can orphan routes. |
| R-18 | **P2** | GUI log output may include hostname/IP, Windows user paths and other environment-specific data. Logs are normally transient, but screenshots/issue posts could leak metadata. | Verified output path, privacy exposure is contextual | Offer explicit privacy-conscious diagnostic summary and avoid public raw logs. |

## 4. User journey re-evaluation

1. **First launch:** Detect ordinary file permissions before attempting writes; explain VPN and network requirements without changing system settings automatically.
2. **Save exception:** Visually distinguish `Saved (not applied)` from `Applied (verified)`; preserve input on failure. Explain that Add does not immediately modify Windows policy.
3. **Apply / UAC:** Clearly explain what needs administrator approval. If approval is cancelled, show `No changes initiated` when verified; never mark a state file as proof of successful operation.
4. **Long-running operation:** Show elapsed time and last confirmed stage; offer *safe* diagnostics rather than promising that force-quitting leaves no residue.
5. **Restart after interruption:** Prefer read-only inspection of the journal and OS objects; if ambiguous, present conflict details rather than automatically deleting third-party rules.
6. **New EXE ZIP folder / network roam:** Detect stale/foreign configuration state, and guide the user about preserving existing state without merging incompatible files.
7. **Reporting a bug:** One-click *redacted* status bundle could include version/commit, error codes and state phase while excluding real IPs, DNS names, file paths and domain entries.

**Safety:** any further live tests must be confined to a disposable, controlled Windows VM with reserved test identifiers, an independent rollback mechanism and no school/production access-control changes. Do not run disruptive fault injection on a personal or managed network.

## 6. Recommended roadmap / user-effort budget

**Sprint A — truthfulness & low-cost recoverability (first):** correct journal-status wording, clear entry only after confirmed successful Add, show pending vs verified states; add failure-state tests and consistent operation/error labels. No new routing behavior.

**Sprint B — ownership and recoverability:** schema validation, protected journal snapshots, an inspection-only recovery report, explicit conflict handling across two portable folders; reject ambiguous ownership. Isolated test fixtures first.

**Sprint C — privilege and supply chain:** signed/helper trust model, verify launch boundary and accessible paths, dedicated code review, pinned Actions and provenance manifest. Do not claim that a signed EXE alone protects all local state.

**Sprint D — user-adapted UX:** keyboard and DPI integration tests, accessible buttons, safer error handling, operation deadlines and nonintrusive update/error diagnostics, minimal-click onboarding.

**Launch gate:** Do not label the app broadly `crash safe`, `domain isolated` or `production secure` until G5–G9 pass and the user-facing claims have corresponding test evidence.
